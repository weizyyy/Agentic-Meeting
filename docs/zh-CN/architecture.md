# 架构

[English](../architecture.md) · **简体中文**

本文说明系统由哪些部分组成、数据如何流动，以及这样设计的原因。字段级的格式见
[interfaces.md](interfaces.md)；Pipecat 的类名与导入路径见 [pipecat-notes.md](pipecat-notes.md)。

## 1. 总览

图中的「实时模型」是用 llama.cpp 部署的情形。它也可以是任意 OpenAI 兼容的 chat completions
接口（配置项 `realtime_llm.mode`），此时该方框位于本项目之外，其余部分不变；两种方式的差别见 §6.1。

设计上有三个主要决定：

1. **推理服务与应用进程分离**。四个推理服务是独立子进程，应用只通过 HTTP 调用它们。
   更换模型、更换显卡或单独重启都不涉及应用代码；其中任何一个也可以换成另行启动的服务。
2. **转录与应答解耦**。转录链路（识别 → 说话人 → 落库 → 字幕）全程运行，不受「是否被唤醒」影响；
   应答链路只在唤醒后启动。实现上靠管线里的先后顺序保证：会议记录器在唤醒门控的上游。
3. **快慢分层**。实时模型只处理一秒左右能够作答的请求；其余交给后台 agent，结果异步回到对话中。

### 设计目标

- 涉及原始音频的环节全部在本地完成，使用开放权重的模型。
- 模型是部署时的选择：路径、接口地址、音色和采样参数来自配置，与模型相关的提示词格式放在
  `config/asr_profiles/` 和 `config/prompts/` 中。
- 一条命令校验配置，一条命令启动并守护全部本地服务。
- 离开本机的数据始终对使用者可见：发往远端实时模型接口的转录，以及每个任务发给 agent 模型的材料。

延迟指标（全部本地服务同时运行、实时模型用 llama.cpp 部署时）：

| 指标 | 目标 |
|---|---|
| 字幕延迟 | 定稿文字落后于语音不超过 1.5 秒 |
| 应答首字 | 说话人停止后约 1 秒（P50 ≤ 1.0 秒，P90 ≤ 1.8 秒） |
| 应答首音 | 首字之后 0.5 秒内 |
| 召回类工具 | 按说话人、时间、关键词检索 ≤ 100 毫秒；含语义检索时 ≤ 400 毫秒 |

实时模型经通用的 chat completions 接口接入时不对上述指标作承诺：前缀缓存与网络延迟不在本项目的控制范围内。

|---|---|---|---|

## 3. 会话时间轴

所有记录用同一把尺子：**会话时间轴**，0 点是本场会议第一帧音频，单位秒。

- 推进方式：服务端每收到一段输入音频，就按采样数累加（采样率固定 16 kHz）。
  `t = 已收到的采样数 / 16000`。不用墙上时钟，因此不受处理延迟和各模块时钟差异影响。
- 识别服务、会议记录器各自对流经自己的音频帧计数。它们看到的是同一串帧，所以结果一致。
  为此，识别服务不会被静音（不发送 `STTMuteFrame`），两者之间也不丢弃音频帧。
- 截图的时间：浏览器在连接建立时与服务端对一次表（见 interfaces.md §5.1），之后每张截图带上
  「按服务端时钟的采集时刻」，服务端换算为会话时间轴。
- 落库时另存会话 0 点对应的 Unix 时间（`sessions.started_at`），需要显示钟点时再相加。

### 3.1 会话生命周期

一场会议对应一个**会话**。会话不等于一次连接：连接可以断、可以换设备，会话要能接着走。

**状态**不另存一列，由数据库里的 `ended_at` 和内存里「有没有活动连接」合起来推出：

| 状态 | 条件 | 页面上能做什么 |
|---|---|---|
| 进行中 | 有一路活动连接挂在这个会话上 | 实时字幕、结束 |
| 已中断 | `ended_at` 为空，但没有活动连接（关页面、刷新、断网、服务重启之后都是这样） | 继续、回看、导出、重命名、删除 |
| 已结束 | `ended_at` 非空 | 继续（重新打开）、回看、导出、报告、重命名、删除 |

**操作**：

| 操作 | 入口 | 行为 |
|---|---|---|
| 新建 | 点「开始新会议」，连接时不带 `session_id` | 建会话，时间轴 0 点 = 此刻；有别的活动连接时先顶替它（那场会议变成「已中断」，之后还能继续）。别的没结束的会议原样留着 |
| 断开 | 关页面、刷新、网络断开 | 只关闭这一路连接，**不写 `ended_at`**，会话变成「已中断」 |
| 结束 | 点「结束会议」 | 断开连接并写 `ended_at`，生成最后一份滚动纪要 |
| 继续 | 点「继续」，连接时带 `session_id` | 见下面的「继续的做法」 |
| 重命名 / 删除 / 合并说话人 | 会议列表 | 删除要二次确认，进行中的不能删；删除同时清掉截图文件和任务目录 |

**同一时刻只有一路活动连接。** 语音识别固定单槽位，说话人区分是一条流，实时模型的上下文也只有一份。
新连接（无论新建还是继续）到来时，服务端先取消旧连接的管线、等它释放资源，再启动新的；
旧页面若还连着，收到一条 `notice`（「已在另一台设备上继续」）并回到未连接状态。

**继续的做法**（`session_id` 在 `POST /api/offer` 的 `requestData` 里，协商之前就校验，找不到返回 404）：

1. **时间轴**：会话时间 = 墙上时间 − `started_at`，在连接建立那一刻对一次表得到 `base_secs`，之后仍按采样数推进：
   `t = base_secs + 已收到的采样数 / 16000`。`base_secs` 不早于时间轴已经用到的地方（上一次连接的终点、最后一条发言的终点）：
   音频时钟和墙上时钟有细微出入，断线后马上重连时不能让时间倒着走。断线期间的空档照实留在时间轴上（页面可以显示「中断了 12 分钟」），
   截图用同一个原点（`captured_at − started_at`），两边天然对得上。每次连接的起止记在 `session_connections` 表里。
2. **说话人区分**：同一进程内继续，复用同一条说话人区分流（说话人编号不变）。流里的时间是「实际喂入的音频累计时长」，
   每次连接记一对（流内时间起点，会话时间起点）做分段换算，断线的空档**不用补喂静音**。
   服务重启后只能新开一条流，编号会重新从 1 起：新流的编号加上该会话已有的最大编号作偏移，
   同一个人因此可能显示为新的说话人（可在界面上合并），但不会把两个人误认为同一个。
   这条流由会话管理器持有（`diar/stream.py` 的 `SessionDiarizer`），连接断开时不释放，所以已中断的会议仍占着说话人区分的显存；
   开始另一场会议、结束或删除这场会议、应用退出时才释放。它出过错的话，下一次连接重开一条（按「服务重启后」处理）。
   合并说话人之后，流里再输出被合并掉的编号也算作合并到的那个人（只在这条流活着的期间有效）。
3. **实时模型上下文**：新建一份 `LLMContext`，内容由数据库重建——最新一份滚动纪要 + 最近 `keep_recent_minutes` 分钟的
   转录行与画面行（与 §6 的压缩是同一段代码）。预热照常。
4. **识别**：每次连接从空窗口开始，`ASRDelta.audio_end_secs` 加上 `base_secs`。
5. **说话人名字、已有发言、截图、任务**：都在库里，原样保留。
6. 服务端在连接建立后发一条 `session` 消息（interfaces.md §6.1），页面据此显示会话信息，再用 HTTP 拉最近的发言补齐。

**未连接时页面也能用**：会议列表、最近对话、导出、报告、重命名、删除都只走 HTTP（interfaces.md §5.1、§5.4），
不需要音频连接。别的设备想「看」一场正在进行的会议，轮询发言接口即可（只读）。

## 4. 管线结构

管线里的处理器顺序（从上游到下游）：

| 顺序 | 处理器 | 来源 | 职责 |
|---|---|---|---|
| 1 | 传输输入（挂**收音增强**滤波器） | Pipecat；滤波器是本项目 | 从 WebRTC 取 16 kHz 单声道音频帧；先过 `audio_in_filter` 把偏低的电平拉到合适范围，再推向下游 |
| 2 | 语音活动检测 | Pipecat `VADProcessor` | 发出「开始说话 / 停止说话」事件帧 |
| 3 | 识别服务 `StreamingASRService` | 本项目 | 只在有人说话时把音频送给识别后端；把增量结果变成转录帧 |
| 4 | 会议记录器 `MeetingRecorder` | 本项目 | 喂说话人区分；把文字归属到说话人并切成发言；落库；推字幕；把定稿发言追加进实时模型的上下文 |
| 5 | 用户侧上下文聚合器 | Pipecat | 唤醒判定、轮次起止判定；唤醒后把用户的话加入上下文并触发模型 |
| 5.5 | 模态闸门 `ModalityGate` | 本项目 | 每个新请求进入模型之前设定这次的应答模态：文字请求只出文字，语音请求照常朗读（§5.5） |
| 6 | 实时模型服务 | Pipecat 的 OpenAI 兼容服务（指向配置里选中的接入地址） | 生成文字、调用工具 |
| 7 | 语音合成服务 | Pipecat（指向本地 `tts-server`） | 文字转语音 |
| 8 | 传输输出 | Pipecat | 把语音送回浏览器 |
| 9 | 助理侧上下文聚合器 | Pipecat | 把助理说出的话写回上下文 |

为什么是这个顺序：

- 收音增强放在 1 里（Pipecat 的 `audio_in_filter`，先滤波、再推帧），而不是单独一个处理器：这样 2、3、4
  以及说话人区分看到的是**同一份**处理后的音频；它逐帧等长输出，不改变采样计数，会话时间轴不受影响。
  必须在 2 之前——语音活动检测有音量门限（默认约 −50 LUFS，见 pipecat-notes.md §3.1），电平偏低的麦克风
  不增益就会被切成碎片（[benchmarks.md](benchmarks.md#麦克风电平偏低)）。
- 2 在 3 之前：识别服务要靠「开始 / 停止说话」事件决定何时送音频、何时收尾。
- 4 在 5 之前：Pipecat 的唤醒策略在未唤醒时会**清空**转录文本，使其不进入上下文。
  记录器必须先拿到转录帧完成落库，再原样放行。
- 4 负责把定稿发言追加进上下文，而不是 5：这样无论是否唤醒，实时模型都「听到了」整场会议。

## 5. 数据流

### 5.1 转录

```
音频帧 ─┬─▶ 识别服务 ──(有人说话时)──▶ 识别后端 ──▶ 增量结果（定稿部分 + 未定稿尾巴）
        │                                              │
        │                                 转录帧（定稿）、临时转录帧（字幕用）
        │                                              ▼
        └─▶ 会议记录器 ──▶ 说话人区分        会议记录器：按时间把文字归到说话人
                             │                         │
                             └── 说话人分段 ──────────▶│
                                                       ├─▶ 字幕消息 ──▶ 浏览器
                                                       ├─▶ 发言落库（停顿或换人时收尾）
                                                       └─▶ 追加一行转录进实时模型上下文
```

要点：

- 识别后端每一步都把「当前音频窗口 + 已定稿文字作为前缀」交给模型续写，末尾若干字符暂不定稿。
  这是识别模型上游的流式算法，本项目在标准 `llama-server` 的音频输入之上实现（见 interfaces.md §3）。
- 检测到停顿时做一次收尾：把尾巴定稿、清空窗口。一次「开始说话 → 停止说话」构成一个识别段。
- 一条**发言**的边界 = 识别段结束，或段内说话人发生变化。
- 说话人结论滞后于文字。发言收尾时用当时的最好判断落库；之后几秒内若说话人区分修订了结论，
  更新数据库并通知界面改标签（已追加进模型上下文的那一行不改）。

### 5.2 实时应答

```
转录帧 ──▶ 唤醒策略：定稿文字里出现助理的名字（英文单词）？
              │ 否：不触发任何应答
              │ 是：开始一个用户轮次；同时通知「预热」上下文缓存
              ▼
        轮次结束判定（停顿 + 轮次结束模型 + 收尾转录到达）
              ▼
        实时模型（关思考、流式）──┬─▶ 文字 ──▶ 浏览器（立即显示）
                                  ├─▶ 语音合成 ──▶ 浏览器
                                  └─▶ 工具调用
                                        ├─ 同步工具（查库）：结果立刻回给模型
                                        └─ 委托工具：立即返回「已受理」，结果晚些到达
```

**唤醒窗口。** 叫到名字后助理进入「醒着」的状态：这一轮说完就作答，朗读时开口可以打断它。
「每次都要叫名字」（`turn.single_activation`，默认）时，助理答完即回到待唤醒状态。Pipecat 自带的策略会一直保持唤醒
直到超时，其间会上任何人的发言都会被当作对助理说的。有人正在说话时助理不会回到待唤醒状态：这要么是打断，
要么是叫完名字停顿之后才说出的要求，待这一轮答完再回到待唤醒状态。`turn.wake_timeout_secs` 是从叫名字到答完的时间上限
（`pipeline/wake.py`、`pipeline/bot.py` 的 `wire_wake_sleep`）。

实时模型可用的工具分三类（清单见 interfaces.md §7）：

- **查库**：召回发言、取滚动纪要、查任务进度。毫秒级，同步。
- **看屏幕**：把最新截图作为图片加入上下文。会多花几百毫秒编码图片。
- **委托**：创建后台任务。工具声明为「不随打断取消」，函数里先回报任务已受理，
  任务结束时再回报最终结果。Pipecat 会把晚到的结果插入上下文并触发一次新的生成，
  助理由此完成口头简报。

### 5.3 截图

```
浏览器：屏幕画面 ─▶ 缩小后与上一张比较 ─▶ 变化超过阈值，或距上次已满兜底间隔
                                              ▼
                                   编码为 WebP ─▶ HTTPS 上传（带采集时刻）
                                              ▼
服务端：校验 ─▶ 落盘 ─▶ 入库 ─▶ 时间线消息 ─▶ 浏览器
                           └─▶ 画面摘要任务（后台槽位，空闲时执行）─▶ 写回数据库
                                                              └─▶ 追加一行「画面」进上下文
```

截图不走 WebRTC 视频轨：视频编码会把幻灯片上的小字压糊，而且浪费带宽。静态图清晰、
时间点明确、只在画面变化时才产生。

**谁看得到原图。** 默认只有三处：生成画面摘要时、实时模型调用 `look_at_screen` 时、实时模型委托任务并要求带屏幕时
（最近的 3 张）。其余环节（上下文、滚动纪要、会后报告）用的是摘要文字。

- `look_at_screen` 不带参数时附上最新的一张，并列出更早的截图（编号、时间、摘要）；实时模型根据摘要判断要不要回看，
  要的话带着编号再调用一次，一次最多看 3 张，看过图再回答。
- `agent.attach_frames` 打开后，交给后台 agent 那个模型的活都带原图：后台任务带到委托时为止的全部截图（不再看实时模型
  要不要带），会后报告带整场的（转录太长要分段时，各段带自己那段时间里的，最后合并的那一次不带），滚动纪要带这一轮
  时间段里的。报告和纪要要由这个模型来写才带（`report.provider`、`realtime.digest_provider` 选 `agent_llm`）。
- 「全部」的口径（`screen/attach.py` 的 `select_frames`）：「无关画面」不带；画面没变的重复截图只带第一张；摘要没生成的照带；
  一次请求超过 `agent.max_attached_frames` 张时均匀抽取，首尾两张一定留。

### 5.4 后台任务

```
委托工具 ─▶ 任务管理器：建任务、排队
                 ▼
          agent 运行器：组装输入（目标 + 相关转录 + 相关截图）
                 ▼
          agent 循环：远端大模型 ⇄ MCP 检索 ⇄ 沙箱里跑代码
                 │  每一步 ─▶ 进度事件（落库 + 推给浏览器）
                 ▼
          结果：口播简报 + 详细内容 + 来源 + 产物文件
                 ▼
          回报给委托工具 ─▶ 实时模型生成一两句简报 ─▶ 朗读
```

- 任务有短编号（`t1`、`t2`…），便于口头指代。
- 「做到哪了」由实时模型调用进度工具回答，读的是最近几条进度事件。
- 简报时机：若此刻有人在说话，等语音活动检测判定停顿后再播；最长等待有上限。

### 5.5 文字输入与应答模态

文字输入是不经过语音的第二个入口：开会时不方便出声，就在页面输入框里打字向助理提问，或委托后台任务。
**什么模态输入，就用什么模态回答**，所以文字请求不会让助理开口说话打扰别人。

```
输入框 ──text_input──▶ 文字入口 ─┬─▶ 会议记录器：落库（source="text"，说话人 −2）、推 utterance、追加上下文行
                                 └─▶ 触发实时模型（不需要唤醒）──▶ 回答文字流式显示；跳过语音合成
```

| 触发 | 回答 | 做法（Pipecat 1.12.0） |
|---|---|---|
| 语音唤醒 | 流式文字 + 朗读 | 请求进入模型前，模态闸门推 `LLMConfigureOutputFrame(skip_tts=False)` |
| 文字输入 | 仅文字 | 文字入口在请求前面放一个记号帧 `TextRequestFrame`；模态闸门看到记号，就在这个请求进入模型前推 `LLMConfigureOutputFrame(skip_tts=True)`。实时模型服务把 `skip_tts` 标在它之后产出的文字帧上，语音合成服务对这类帧直接放行、不合成 |
| 后台任务完成播报 | 沿用**委托当时那一轮**的模态（任务记录里存 `modality`） | 文字委托的任务：播报前后同样各推一个配置帧 |

规则：

- 模态按**每一次请求**设定，设定点在模型入口（`pipeline/modality.py`）。不能用「文字请求前后各推一个配置帧」的做法：
  模型先调工具、结果回来再生成一次才是真正的回答，而「恢复朗读」的帧在两次生成之间就生效了，
  工具之后的回答会被念出来。工具结果触发的再次生成走的是向上游的上下文帧，不经过闸门，沿用这次请求的模态。
  语音合成关闭时文字入口不放记号（没有东西可关）。
- 已知的边界：一个请求的工具还没执行完时又来了另一种模态的请求，后到的会改掉模态。工具执行很短，文字入口在助理忙时也排队，实际很难碰到。
- 「助理忙」包含工具执行期间（两次生成之间）：这时文字请求照样排队，后台模型不恢复，上下文也不压缩。
- 文字请求**不打断**正在进行的朗读或生成：助理忙时排队（先进先出，最多 5 条），空闲后依次处理。
  别人正在说话不算忙——文字回答不出声，不会打扰。
- 文字输入不依赖唤醒窗口，也不影响语音那条路径的唤醒状态。

## 6. 实时模型的上下文管理

能否在一秒左右作答，取决于实时模型每次只需处理**新增**的上下文。`llama-server` 会缓存
上一次请求的前缀；只要这次请求以同样的内容开头，就只计算新增部分。因此有三条规则：

1. **只追加**。上下文 = 系统提示词 + 工具定义 + 按时间追加的消息。任何对前面内容的改动都会
   让缓存整体失效，所以说话人改名、标签更正都**不回改**已在上下文里的行。
2. **空闲时压缩**。上下文超过预算（配置项 `realtime.context_budget_tokens`）后，
   挑一个没人对助理说话的时刻，把较早的转录替换成滚动纪要，只保留最近若干分钟原文
   （用整体替换上下文的帧），然后立刻做一次预热。
3. **预热**。两种触发：唤醒词被识别到的那一刻（用户还要说几秒才说完，正好利用这段时间）；
   以及每隔一段时间的定时预热。预热 = 用**与正式请求完全相同的消息和工具定义**
   向同一个槽位发一次只生成 1 个 token 的请求。

并发槽位的分工：槽位 0 只用于实时应答和预热；槽位 1 用于画面摘要和滚动纪要。
检测到唤醒时，取消槽位 1 上正在进行的请求，把 GPU 让给应答。

「让路」的实现（`pipeline/activity.py`、`pipeline/background.py`）：

- **助理忙** = 从被叫到名字（或收到文字请求）开始，到这一轮生成完、朗读完为止。叫了名字却没有下文时，
  以唤醒窗口过期为准，另有 60 秒的看门狗兜底。从忙到闲有 0.5 秒延迟，免得在「生成完」与「开始朗读」之间来回切。
- **后台模型的入口只有一个**（`BackgroundModel`）：串行（后台只有一个槽位）、忙时暂停、暂停的同时取消在途请求。
  被取消的那次由发起方决定重做还是放弃——画面摘要会重做这一张，除非期间又来了更新的画面。
- 上下文的压缩和预热用同一个忙闲信号做互斥。
- 连接断开时一律恢复，不会因为断在应答中途就一直停着。

三条规则的实现（`pipeline/context.py`）：

- **估算**：中文 1 字 ≈ 1 token、其余 4 个字符 ≈ 1 token；每条消息另加 4；上下文里的图片每张按 1500 算
  （不去数 base64）；系统提示词和工具定义算一次。每 5 秒看一次，不调分词接口。
- **压缩**：估算值超过预算、助理完全空闲、距上次压缩已过 60 秒时触发。先让滚动纪要补到最新（补不成也不拦着），
  再从数据库重建：`【此前会议纪要】` + 纪要没纳入的发言和最近 `keep_recent_minutes` 分钟的发言、画面行。
  原文从「纪要纳入到哪」和「最近若干分钟的起点」里**更早**的那个开始，中间不留空档；光是最近的原文就超预算时，
  把保留时长逐次减半（最少一分钟）。还没有纪要而较早的内容被丢掉时，放一条说明，提示可以用 `recall` 查。
  助理说过的话重建成 assistant 消息；工具调用的记录和看过的截图不保留。
- **重建必须经过会议记录器**（`rebuild_context`）：它和「发言落库 + 追加上下文行」共用一把锁。
  否则重建读完数据库之后才落库的发言，会先被追加、又被替换帧整个盖掉，从上下文里消失。画面行也经过记录器追加
  （`append_context_line`），排在同一个顺序里。
- **预热**：`cfg.realtime_llm.cache_warm` 为假时完全不做（不建请求、唤醒时也不发）。为真时三个触发点：
  检测到唤醒词（这时助理算「忙」，后台模型让路，但预热照发——它正是为这次应答做的）、压缩之后、
  每 `cache_warm_interval_secs` 的定时器（上下文自上次预热以来没变就跳过）。助理正在生成或朗读时不发；
  同一时刻只有一次在途；失败只记日志。预热请求由 `RealtimeLLMService.warm_cache` 发出，参数来自和正式请求
  同一段代码（`request_params`），只改 `stream=False`、`max_tokens=1`。

### 6.1 两种接入方式的差别

实时模型的接入方式由配置项 `realtime_llm.mode` 决定。管线结构、工具、上下文格式以及只追加与压缩的规则
在两种方式下完全相同；差别仅限于下表所列各项，并且都收敛在配置对象的几个属性中，
业务代码只读取这些属性，不按接入方式分支：

| 事项 | 方式一 `llama_server` | 方式二 `openai_api` | 代码里看什么 |
|---|---|---|---|
| 进程 | 本项目可代为启动（`launch.enabled`） | 不管理；只做连通性检查 | `cfg.realtime_llm.managed` |
| 地址、模型名、密钥、采样、是否识图 | 各自小节里的同名字段 | 同左 | `cfg.realtime_llm.active` |
| 请求附加字段 | 用户的 `extra_body` + 槽位号 + `cache_prompt` | 只有用户的 `extra_body` | `cfg.realtime_llm.request_extra_body(background=...)` |
| 实时与后台任务的隔离 | 各占一个槽位，互不冲掉对方的缓存 | 没有槽位；后台任务与实时应答打到同一个接口 | 同上 |
| 缓存预热 | 始终进行 | 默认关闭，可按需开启 | `cfg.realtime_llm.cache_warm` |
| 关闭思考 | 启动参数 `--reasoning off`（必要时再加模板参数） | 因服务而异，写入 `extra_body` | — |
| `developer` 角色 | 不支持，转成 `user` | 默认按不支持处理，可配置 | `cfg.realtime_llm.supports_developer_role` |
| 数据去向 | 本机 | 可能离开本机，此时给出提示 | `config.check_warnings()` |

「唤醒时取消后台请求」在两种方式下都要做：方式一是为了让出 GPU，方式二是为了不和实时应答抢同一个
接口的并发额度。

上下文里各类内容的格式（实时模型的系统提示词会解释这些约定）：

```
[00:14:02 王老师] 这个 baseline 的学习率是不是设大了
[00:14:09 说话人3] 我回去再跑一组对比
[画面 00:14:30] 幻灯片：消融实验结果表；去掉数据增强后验证集准确率下降 2.1 个点
[任务 t2 完成] 已核实该论文在 Google Scholar 的引用数为 1,243
```

## 7. 预算

### 7.1 延迟

| 阶段 | 预期耗时 | 影响因素 |
|---|---|---|
| 判定「说完了」 | 0.2–0.4 秒 | 语音活动检测的静音阈值；轮次结束模型在 CPU 上约十几毫秒 |
| 收尾转录到达 | 0.1–0.3 秒 | 识别后端做最后一步 |
| 实时模型首字 | 0.1–0.2 秒 | 前提：关思考、前缀已缓存 |
| 首句生成 + 语音首包 | 0.3–0.5 秒 | 取决于模型生成速度与语音合成首包延迟 |

以上为方式一下的预期值。实测结果（包括经 chat completions 接口接入时的整场会议实测）见 [benchmarks.md](benchmarks.md)。

### 7.2 显存

实测值（详见 [benchmarks.md](benchmarks.md)）：

| 组件 | 实测占用 | 说明 |
|---|---|---|
| 语音识别（Q8 量化，上下文 8192） | 约 3.8 GB | 比按文件大小估的多，主要是音频编码器的工作内存 |
| 说话人区分 | 约 0.2 GB | |
| 语音合成（0.6B，Q8） | 约 2.4 GB | |
| 嵌入模型 | 0 | 前提是启动参数里有 `--device none` |
| 实时模型 | 取决于所选模型 | 估算方法：权重文件大小 + 识图投影文件大小 + 上下文缓存（按 32 KB/token，32K 上下文约 1 GB）；走非本机的接口时不占本机显存 |

多显卡时的推荐分配：大卡放实时模型和语音合成，小卡放语音识别和说话人区分。
这样识别的持续计算不会与实时模型争抢同一块 GPU。
例如 22 GB + 6 GB 两块卡：小卡用掉约 4 GB，大卡除语音合成外还剩约 18 GB 给实时模型。
配置写法见 [runtimes.md](runtimes.md) §5。

只有一块 24 GB 显卡时，上面三项合计约 6.4 GB，留给实时模型约 17 GB。

## 9. 故障与降级

**转录的优先级最高。** 应答、任务、截图、存储任何一环出现故障，都不能使识别和字幕中断。

| 故障 | 表现 | 处理 |
|---|---|---|
| 语音合成服务不可用 | 没有语音 | 文字应答照常；界面提示「语音不可用，助理这次只出文字：<原因>」（`pipeline/errors.py`，同类提示 30 秒内只发一次） |
| 嵌入服务不可用 | 语义检索不可用 | 召回退回关键词检索；回填退避重试，恢复后补上 |
| 画面摘要失败（后台模型出错、不识图、被关掉） | 截图没有摘要 | 截图照常进时间线；该张记为 `failed` / `skipped`，不影响后面的；`look_at_screen` 仍可直接看图 |
| 截图落盘失败、上传被拒 | 时间线缺这一张 | 页面提示一次，之后每个节拍照常重试；转录不受影响 |
| 说话人区分加载失败 | 不分说话人 | 所有发言记为「未知」，其余照常；界面提示 |
| 识别服务请求失败 | 字幕停止 | 指数退避重试；连续失败时界面提示，音频计时不中断 |
| 收音增强滤波器出错 | 无（对用户不可见） | 该帧原样放行并记日志，转录不受影响；不能因为增益算法的问题丢帧 |
| 麦克风电平过低（增益已到上限仍然很轻） | 字幕断断续续或没有 | 日志里打印输入电平；界面提示「麦克风音量过低，请调高系统输入音量」 |
| 实时模型不可用（本地服务挂掉，或远端接口不通、密钥失效、限流） | 无法应答 | 转录照常；请求失败时界面提示「助理暂不可用：<原因>」（连不上、密钥被拒绝、限流、超时……） |
| 远端大模型或 MCP 不可用 | 任务失败 | 任务标记失败并带原因；助理口头说明没做成 |
| 未装 Docker | 无法执行代码 | agent 仍可检索与读图；需要跑代码的步骤如实报告做不了 |
| 浏览器断线 | 采集中断 | 客户端自动重连；服务端保留会话，重连后时间轴接着走 |
