## 整场会议回放

**素材。** 一段 50 分 29 秒的真实座谈录音：一位主持人和多位嘉宾轮流发言，带有口音、语气词和掌声。

**方法。** `scripts/soak.py` 通过 WebRTC 把录音按实际速度送入完整的应用（输入增益、语音活动检测、识别、
说话人区分、存储，以及用于应答的实时模型和语音合成），每七分钟用合成语音呼叫一次助理，并发送一条文字提问。

### 转录

| 指标 | 结果 |
|---|---|
| 存储的发言 | 209 条，共 12 294 字；平均每条 59 字，最长 233 字（相邻片段合并之后） |
| 说话人 | 区分出 8 位，这是说话人区分模型的上限；录音中约有 9 人发言。另有 5 条很短的发言未能归属 |
| 字幕延迟（发言定稿时，已送出的音频时长减去该发言的结束时间） | 中位 0.70 秒，P95 0.78 秒，最大 2.06 秒；全程保持稳定 |
| 滚动纪要 | 21 份，每五分钟一份；最后一份约 2 400 字 |
| 上下文压缩 | 一次，发生在第 31 分钟：估算 25 900 → 6 900 token（预算 24 000） |

### 应答延迟

从语音请求结束时起算，包含 0.2 秒的语音结束判定：

| 指标 | 结果 |
|---|---|
| 唤醒 → 首字 | 中位 1.5 秒（0.95–2.8 秒） |
| 唤醒 → 首音 | 中位 2.5 秒（1.7–3.7 秒） |
| 文字提问 → 首字 | 中位 2.1 秒（0.8–3.0 秒）；多数文字提问先触发了一次工具调用 |

服务端日志中一次不含工具调用的应答的延迟拆分：

| 环节 | 耗时 |
|---|---|
| 语音结束判定（`turn.vad_stop_secs`） | 0.20 秒 |
| 收尾转录 | 0.10–0.13 秒 |
| 轮次结束模型 | 0.03–0.08 秒 |
| 实时模型首字 | 0.45–1.0 秒，随会议时长增加：该接口每次请求都重新处理整个上下文，一次预热请求本身也需要 0.7–1.2 秒 |
| 累积出第一句话 | 0.3–0.5 秒 |
| 语音合成首包 | 0.24–0.36 秒 |
| 合计 | 1.4–2.3 秒 |

以上是实时模型经通用接口接入时的数据。[architecture.md](architecture.md#设计目标) 中一秒的指标针对
llama.cpp 部署方式，该方式尚未进行实测。

### 唤醒的可靠性

在第一轮测试中，8 次语音请求有 3 次未被应答；此外，助理在一次应答之后对其他与会者的发言作出了反应。
两个现象都已查明原因并做了修改：

| 现象 | 原因 | 修改 |
|---|---|---|
| 转录中名字缺失或被截断（`ova`、`No one`、「诺亚」） | 在「名字，停顿，请求」这样的句子中，名字只持续几百毫秒。语音活动检测往往到请求部分才触发，而此前只有 0.3–0.5 秒的音频会送入识别 | `asr.preroll_ms` 的默认值由 300 毫秒提高到 1500 毫秒 |
| 应答之后，助理对其他人的发言作出反应 | Pipecat 的唤醒策略会保持唤醒直到 `wake_timeout_secs` 到期 | 助理答完即回到待唤醒状态（`wire_wake_sleep`） |

使用同一批合成的语音请求、每 33 秒一次的对照测试：

| 句首回补时长 | 成功唤醒 |
|---|---|
| 500 毫秒 | 14 次中 9 次；另一轮 11 次中 6 次 |
| 1500 毫秒 | 12 次中 11 次（有一次名字被识别成了无关的词） |

同样的音频绕过语音活动检测、直接送入识别后端时，6 次全部识别正确，说明丢失的原因是音频开头缺失，
而不是识别模型本身。名字偶尔被写成近似的词（`novel`、「诺亚」），这类写法可以登记到
`session.wake_aliases` 中。

### 50 分钟内的资源占用

| | 开始 → 结束 |
|---|---|
| 应用进程内存 | 320 MB → 512 MB；五分钟时为 504 MB，此后保持平稳 |
| 语音合成进程内存 | 2.7 GB，不变 |
| 识别与嵌入两个 `llama-server` 进程 | 4.9 GB → **14.5 GB**，在前 15 分钟内上升 |
| 显存（全部服务位于 22 GB 的显卡） | 14.6 GB → 14.8 GB |

增加的 8 GB 是 `llama-server` 保存在主机内存中的提示缓存（`--cache-ram`，默认上限 8 192 MiB）。
识别请求之间没有公共前缀，这份缓存不起作用。现在识别和嵌入服务以 `--cache-ram 0` 启动，
相同负载下两个进程合计稳定在约 5 GB。

### 最终配置下的复测（33 分钟）

完成上述修改（句首回补 1500 毫秒、`--cache-ram 0`、答完即回到待唤醒状态）之后重新进行了回放。
原计划运行两小时，在第 33 分钟时手动停止，因此**连续运行两小时尚未得到验证**；
目前最长的连续运行仍是上文的 54 分钟。

| 指标 | 结果 |
|---|---|
| 语音请求 | 4 次全部得到应答 |
| 文字提问 | 3 次全部得到应答；首字 2.0–2.1 秒 |
| 字幕延迟 | 每十分钟的中位数为 0.70–0.72 秒，最大 1.8 秒 |
| 应用进程内存 | 325 MB → 508 MB（第 10 分钟）→ 511 MB（第 30 分钟） |
| `llama-server` 进程 | 4.9 GB → 5.1 GB，此后不变 |
| 语音合成进程内存 / 显存 | 2.7 GB 不变 / 14.6–15.1 GB |

这一轮语音请求的首字延迟为 4.0–5.7 秒。对其中一次请求的日志分析显示：轮次结束模型判定这句合成的问句尚未说完，
管线等待了三秒的兜底时间；实时模型自身的首字延迟为 1.2 秒。句首回补加长之后，名字被识别为独立的一段，
请求部分因而作为单独的一轮接受判定。自然语音是否有同样的表现尚未测量。把 `turn.smart_turn` 设为 `false`
可改用固定 0.6 秒的停顿判定。

## 截图、工具、任务与报告

在进行中的会议里使用合成的幻灯片测得：一类是标题加几行文字，另一类是三列共 21 个数字的表格。

| 项目 | 结果 |
|---|---|
| 画面变化检测 | 两页白底、仅文字不同的幻灯片，按整张缩略图取平均只相差 0.9–1.3%，低于 4% 的阈值，后一页因而沿用了前一页的摘要。改为取变化最大的小块之后，差值为 9–14%（同一画面重新压缩为 0.1%），每页都得到了各自的摘要 |
| `look_at_screen` | 询问当前页面时只使用最新的截图。询问此前一张表格中的两个数字（摘要中没有）时，模型按编号调取了那张截图并回答正确。需要对照两张表格的问题使它又调取了第二张。摘要中已有答案的问题没有引起额外的调取 |
| 召回 | 询问 40 多分钟前某位嘉宾的观点，以及「谁提到过……」，均回答正确并指出了说话人 |
| 后台任务（联网检索） | 「查询某机构的成立年份和规模」：192 秒，附来源；其间询问进度可以得到回答 |
| 后台任务（沙箱） | 「计算四个数的平均值和标准差」：41 秒，结果正确 |
| 附带截图的后台任务（`agent.attach_frames`） | 三张截图全部附带；agent 从图中读出六个数字，并在沙箱中画出分组柱状图，耗时 47 秒 |
| 附带截图的滚动纪要与报告 | 分别为 15 秒和 20 秒（各附三张图）；纪要中引用了只在图中出现的数字 |
| 单次请求附带 40 张 1920×1080 的图片 | 28 秒；图片数量和抽查的三页内容均正确 |
| 会后报告 | 60 分钟的会议（输入约 1.6 万 token）：思考强度为 medium 时 38 秒，关闭思考时 13 秒；六个部分齐全 |
| 导出 | Markdown 转录 66 KB，JSON 252 KB，压缩包含转录、JSON、报告、截图和任务产物 |

在测试所用的接口上（上报的上下文长度为 262 144 token，单次请求最多 999 张图片），
一张图片约每 1 024 个像素占用一个 token：1280×720 约 880 个，1920×1080 约 2 040 个。

测试中发现的两个问题：

- 开启思考时，生成报告的模型把 4 096 token 的输出额度全部用于思考，返回了空的报告。
  现在由 `agent.generation_max_tokens`（默认 16 384）为直接生成设置更宽的额度。
- agent 在最终回答的 JSON 字符串中直接写入了换行符，严格解析因此失败。结果解析现已接受这种写法。

## 实时模型的工具选择

`scripts/eval_realtime_model.py` 运行 16 条固定样例（几行转录加一句请求），每条三遍。

| 指标 | 结果 |
|---|---|
| 首字延迟 | 中位 0.38 秒，最大 0.49 秒 |
| 应调用工具时选择正确 | 33 / 33 |
| 不应调用工具时未调用 | 15 / 15 |
| 直接回答的长度 | 中位 40 字，最长 85 字 |

提示词的改动会明显影响这一平衡。曾在提示词中加入一句「调用工具前不要先说话」，结果在 15 个无需工具的样例中
有 7 个调用了工具，该句已移除。修改 `config/prompts/realtime_system.md` 之后请运行此脚本。

## 故障注入

对 [architecture.md §9](architecture.md) 故障表中的各项，在运行中的系统上逐一进行了验证。

| 注入的故障 | 观察到的表现 |
|---|---|
| 实时模型指向不可达的地址 | 转录照常；语音和文字请求均无应答；页面显示「助理暂不可用：连不上服务」 |
| 语音合成指向不可达的地址 | 文字应答照常，并提示「语音不可用」；应答内容照常保存并留在上下文中，助理可以应要求复述上一次的回答 |
| 说话人区分模型替换为无效文件 | 连接时给出提示；字幕不带说话人；转录与应答不受影响 |
| 会议中途结束嵌入服务进程 | 召回通过关键词检索继续回答 |
| 会议中途结束识别服务进程 | 10 秒后给出提示；用 `services up` 重新启动该服务后，字幕在 12 秒内恢复 |
| 强制结束 `serve --with-services` | 三个推理进程均由操作系统结束。引入作业对象之前，它们会残留并继续占用端口和显存 |
| 强制结束应用后重启，并继续会议 | 时间轴接续，上下文由纪要和最近的转录重建，说话人重新编号并给出提示 |

## 单项测试

除上游提供的样例音频外，本节使用的语音均为合成语音，由不同音色扮演不同的与会者，比真实会议干净得多。
这些数据说明各组件工作正常、时间戳对齐、性能有余量，并不代表真实场景下的准确率。

### 语音合成

| | GPU 版 | CPU 版 |
|---|---|---|
| 实时率 | 0.19 | 约 1.1 |
| 流式首字节 | 0.08 秒（启动后的首次请求为 0.24 秒） | 约 0.2 秒（首次约 1 秒） |
| 输出 | 24 kHz、16 位、单声道 PCM，分块返回 | 同左 |

### 流式识别

滚动窗口、前缀续写、每一步按新增音频分配 token 预算、回退一个 token（interfaces.md §3.2）。步长 320 毫秒。

| 指标 | 结果 |
|---|---|
| 上游样例（6.7 秒中文） | 与整段识别的结果一致，仅少一个逗号 |
| 模拟会议（90.5 秒、10 句、4 种音色，含一句 28 秒的长发言） | 字错误率 0.3%（326 字中错 1 字） |
| 单步耗时 | 中位 0.09 秒，最大 0.18 秒（16 秒窗口填满时） |
| 定稿文字落后于音频 | 中位 0.09 秒，最大 0.24 秒（不含语音活动检测和说话人区分的延迟） |
| 服务启动 | 约 3 秒就绪 |
| 首次请求 | 在一台机器上最初两次使用时分别约为 17 秒和 9 秒，此后每次重启后均为 0.2 秒，推测是显卡驱动在编译并缓存计算内核。更换机器、驱动或运行时版本后会再出现一次 |

算法中包含由以下两点发现而来的处理：

- **宽松的生成预算加按字符回退，输出质量很差。** 每一步允许生成 32 个 token 并保留末尾四个字符不定稿时，
  会出现丢字、多余的标点和句子截断。模型按「只输出已稳定的内容」训练，预算宽松时会抢先输出；
  按字符回退还可能把一个 token 切开。改用上游服务端的做法后问题消失。
- **段落开头可能照抄热词。** 音频很短或接近静音时，模型有时会原样输出 system 消息中的热词表，
  还可能造成误唤醒。因此，未定稿的输出若以「从第一个热词起连续两个以上的热词」开头，将被丢弃。

### 唤醒词匹配

四个候选名字（Jarvis、Nova、Friday、Echo），每个名字七句话（五句应当唤醒，名字分别位于句首、句中、句尾；
两句不应唤醒），四种音色，语音直接送入识别后端：

| 本项目的 `WakeWordUserTurnStartStrategy`（修正了词边界） | 每个名字 7 / 7 |

## Windows 上的回环连接

| | |
|---|---|
| 连接无人监听的回环端口 | 原始套接字需要 2.07 秒才返回「连接被拒绝」；httpx 连接 `127.0.0.1` 为 2.27 秒，连接 `localhost` 为 2.33 秒。Windows 会对回环连接进行重试，而不是立即拒绝 |
| 影响 | 对尚在启动的服务，每次健康探测浪费约 2 秒；依次探测四个服务会多出约 8 秒 |
| 对策 | 回环地址的探测使用 0.5 秒的连接超时（`services/supervisor.py` 中的 `LOOPBACK_CONNECT_TIMEOUT_SECS`），启动前的探测并发进行 |
| 效果 | 四个服务均未运行时，`services status` 在 0.7 秒内返回 |

Linux 和 macOS 会立即拒绝连接；上述对策在这些平台上没有副作用，因此未按平台区分。

## 麦克风电平偏低

### 现象

使用物理麦克风时，语音要么完全无法识别，要么每句话只识别出零星几个字。用同一支麦克风录制的音频在正常的
回放音量下几乎听不见，调高音量后可以听清，说明采集到的电平本身偏低。合成语音和样例音频的电平较高，
不会暴露这一问题。

### 原因：语音活动检测的音量门限

Pipecat 的 `VADParams.min_volume` 默认为 0.6。一帧被判定为语音需要同时满足 `置信度 ≥ 0.7`
**和** `平滑音量 ≥ min_volume`。这里的音量是最近 0.4 秒的 BS.1770 响度，由 −110…−10 LUFS 线性映射到 0…1，
再经指数平滑，因此 **0.6 约对应 −50 LUFS，每降低 6 dB，数值约减少 0.06**。输入过轻时只有最响的音节能通过门限，
「开始说话」与「停止说话」事件变得零碎，而语音识别只在检测到语音时才接收音频，于是每句话只能得到几个字。

`scripts/mic_check.py` 可以复现这一测量：把一段 11 秒的自然语音样例
（`third_party/NeMo-Speech.cpp/test_files/asr/wav/test/jfk.wav`，RMS −16.9 dBFS）按不同幅度衰减，
以 20 毫秒为一步送入 Pipecat 的语音活动检测，统计被判定为语音的步数占比和「开始说话」的次数。

| 衰减 | RMS（dBFS） | 门限 0.6：语音占比 / 开始次数 | 关闭门限：语音占比 / 开始次数 | 平滑音量峰值 |
|---|---|---|---|---|
| 0 dB | −16.9 | 0.44 / 6 | 0.46 / 6 | 0.99 |
| −12 dB | −28.9 | 0.45 / 8 | 0.45 / 8 | 0.87 |
| −24 dB | −40.9 | 0.40 / 8 | 0.43 / 10 | 0.75 |
| −30 dB | −46.9 | 0.27 / 9 | 0.38 / 7 | 0.69 |
| −36 dB | −52.9 | **0.07 / 1** | 0.40 / 9 | 0.63 |

样例中包含停顿，因此占比小于 1；应比较各行之间的相对变化。

- 衰减 36 dB（RMS 约 −53 dBFS）时，默认的门限几乎丢弃了整段语音。关闭门限后，
  语音活动检测模型自身的置信度几乎不受电平影响。
- 对策分为两层：首先提高电平（系统输入音量、麦克风加强，或 `[audio]` 中的服务端自动增益），
  其次保留对门限的调节手段（`turn.vad_min_volume`）。

### 未测量的内容

- 浏览器自带的自动增益在具体设备上是否生效。Pipecat 客户端请求麦克风时没有附带音频约束
  （pipecat-notes.md §12）。
- 门限放开且不加增益时，识别模型自身对低电平音频的容忍程度。
